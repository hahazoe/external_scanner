## Lua 性能统计工具准确性审计（6 个探针）

用户问"这套 lua 性能统计准不准、有没有漏洞"。做法：读 lua_profiler.c /
lua_api_hooks.c / telemetry_writer.c / injected_runtime.c，再用真实 Lua 5.1.4
编译独立探针复现（探针在 `temp/`，日志在 `build/probe*_utf8.txt`）：

| 探针 | 文件 | 复现的结论 |
|---|---|---|
| 1 | temp/root_inclusive_probe.c | 同帧第 2 个根调用 inclusive 记为 0（真值 ≈6.3ms） |
| 2 | temp/hook_overhead_probe.c | 30 万调用：20.8ms → 158.3ms（7.6×），≈0.23µs/事件 |
| 3 | temp/line_sample_probe.c | 行采样=指令数采样：60ms 的 C 忙行 0 样本，1.4ms 纯 VM 行 100 样本 |
| 4 | temp/error_unwind_probe.c | pcall 接住的错误导致影子栈残留死帧，跨帧永久存在 |
| 5/6 | temp/line_repro_probe.c, intern_probe.c | 字典 `strncpy(255)+strncmp(256)`：≥255 字符 key 永不去重；满 4096 后新 key 返回 0 |

结论已写入 MEMORY.md「lua_profiler 已知失真点」。未改任何产品代码；
如需修复，建议优先级：错误展开 → 根调用 inclusive → 字典 key 比较 → 行采样缓存。
回归测试可加进 `tests/lua_profiler_core_test.c`（现缺"同帧多根调用""错误展开"两例）。

## 修复核心失真点（P0-1 / P0-2 / P1-3）

按上面优先级修了三处，`-Wall` 零警告，step 2/5/6/7 全绿（日志 `build/final.txt`）。

1. **P0-2 同帧多根调用 inclusive=0** — `lp_profile_hook` 里 `thread->logical_qpc = 0`
   原来在 hook 末尾做，新帧在之前就把 `frame_logical_start` 记成了上一轮根调用的残留值。
   改为在 is_call 分支里、push 之前重置（`tests/lua_profiler_core_test.c` 的
   `cocos_debug_lua_profiler_test_call` 桩同步改）。删掉末尾那行重置。

2. **P0-1 错误展开残留死帧** — 新增受保护调用边界跟踪：
   - `LpThread.pcall_base[32]`（token + stack_top + overflow_depth），`g_pcall_token` 单调发放
   - 新 API `cocos_debug_lua_profiler_protected_enter/leave(L, tracked, status)`
   - `lua_api_hooks.c` 新增 hook `lua_pcall`（install 返回位掩码加 bit2=4；
     `injected_runtime.c` 里装不上就报 error 拒绝出数据，理由是静默错数据更糟）
   - `lp_drop_frames_locked(thread, target_top)`：截断到边界深度；**最外层被丢弃帧保留自己的
     self 时间，内层帧的时间归并给它**（只是从各 acc 转移，不丢），这样
     `sum(method self) == lua_cpu` 与 `script+c == cpu` 两个不变量在出错的帧里仍然成立
   - `resume_leave(L, status)` 签名加 status：coroutine 带错误返回即死亡，
     直接清空它的影子栈（否则线程永远 running 且持有永不 pop 的栈）
   - 未做的：不动 `lp_rebuild_stack_locked`。曾考虑在 frame_begin 全量重同步，但
     `lua_getstack` 跳过 tail call（OP_TAILCALL 会先发 CALL hook 再合并 ci），
     按真实深度重同步会误删合法的尾调用帧，风险大于收益。

3. **P1-3 字典 key ≥255 字符永不去重** —
   - `telemetry_writer.c::intern_method`：先 `strncpy` 截断到 255 再算 hash/比较，
     原来 hash 用全长、比较用 `strncmp(...,256)`，≥255 字符的 key 永远不等于自己的副本，
     每次调用吃一个槽位；4096 槽（进程级、永不清零）打满后新方法 method_id=0
   - `lua_profiler.c::lp_sample_line_local`：不再 intern 原始 `ar->source`（loadstring 场景
     就是整段源码），改 intern `"@src:" + ar->short_src`（≤60 字符，天然有界）
   - 结论修正：`g_method_meta_count` 在 `start()` 不清零**并非** bug——writer 字典本身也不清，
     清掉本地表只会重新 intern 得到同样的 id；不清反而省一次 intern。不要再"修"它。

**新增回归测试**（都做了反向验证：把两处修复临时改回旧写法，测试确实红）：
- `tests/lua_profiler_core_test.c`：`test_two_root_calls_in_one_frame`（断言第 2 次根调用
  inclusive==30；旧代码得 20）、`test_protected_error_unwind`（断言死帧不残留、
  出错帧里 self 之和仍等于 lua_cpu）
- `tests/lua_profiler_lua51_test.c`：真 Lua 5.1 + 真 `lua_pcall` hook，`boom()` 抛错被接住后
  同帧继续跑 `after()`，断言无方法 `active_at_end != 0`（旧代码红）
- `tests/ipc_selftest.c`：899 字符长 key 去重 + `dictionary_count` 只涨 1

仍未修（按设计保留，只在文档里标注）：P1-4 hook 自身开销未扣除（≈0.23µs/事件，
进 body_ms 不进 lua_cpu，因为 hook 体时间本来就落在两次 lp_now 之外）、
P2-5 行采样是指令数采样非时间采样、P2-6 lua_cpu 是"在 Lua 里的墙钟"且帧窗口=drawScene body。

→ 需补 Texture2D::initWithImage / GLProgram::link / SpriteFrameCache::addSpriteFrames 插桩。

**C 类（2 帧最差）：`PackageData.luac:394 getObjectThisIDByBaseID`（114 次/帧）+ `:922
GetObjectNumByBaseId`（12 次）线性扫描，叠 patch 重定义的全局 tonumber（`main.luac:266`，
9413 次/帧 → 6.0ms）。seq 2063 body 89.97ms 是全程最大。

**重要工具侧发现（P1，建议修 profiler）**：`lua_wall` 被静默截断。
`lp_union_thread_intervals` 的忙区间是"每个 hook 事件一个区间"（开行采样时 exit_qpc=lp_now()，
相邻区间不合并），而 `LP_LOCAL_INTERVAL_CAP=4096`（lua_profiler.c:15），超出即丢弃并置
`INTERVAL_LIMITED(0x80)`。本录制 hook_events 均值 6855/帧 → 756/969 帧被截断。
**判据：`cpu - wall > 0` 当且仅当 0x80 置位**（flags=0 的 209 帧差值恒为 0.00），
`r(cpu-wall, hook_events)=+0.926`，`(cpu-wall)/hook_events` 稳定 0.29–0.51µs。
→ **分析录制一律用 `lua_cpu` 不用 `lua_wall`**，先看 `flags & 0x80`。seq 2063 两者差 21 倍。
